# 実装上の必須の注意

**コードを変更する前に読むこと。** いずれも実際に踏んだもので、静かに壊れて
気づきにくい種類のものだけを集めてある。

## OpenCvSharp と画像の読み書き

- **`Mat` は必ず `using` で破棄する。** GC の管理外のネイティブメモリであり、プレビュー更新のたびに生成して放置するとメモリが際限なく増える
- **AnyCPU にしない。** OpenCvSharp のネイティブ DLL は x64 のみで、`DllNotFoundException` の原因になる
- **`Cv2.ImRead` は使わない。** ファイル名を ANSI でネイティブへ渡すため、
  CP932 外の文字を含むパスで ArgumentException が発生し、一括処理が
  中断する。`File.ReadAllBytes` + `Cv2.ImDecode` を使うこと
- **`Cv2.ImWrite` も使わない。** 読み込みと同じ理由で、CP932 外の文字を含む
  出力パスで失敗する。`Cv2.ImEncode` + `File.WriteAllBytes` を使うこと。
  なお書き込みは**一時ファイル名で行い、完了後に `File.Move` で改名する**。
  中断や失敗で中途半端なファイルを残さないため（原則 2 に直結する）。
  **その `ImEncode` は Exif を書き出さない**ので、Exif の削除は既定の挙動に
  なる。実装が必要なのは「残す」ほう（詳細は [design.md](design.md) の「出力」の Exif）
- **`ImDecode` は Exif の Orientation を適用済みで読み込む**（検証済み。
  ImRead と寸法・回転方向とも一致）。自前で回転補正を加えると二重に回るので、
  絶対に追加しないこと。回さずに読みたい場合は
  `ImreadModes.IgnoreOrientation` を使う
- **`ImreadModes.Unchanged` は Exif の Orientation を適用しない**（実測で確認済み。
  `IMREAD_UNCHANGED` は `-1` で `IMREAD_IGNORE_ORIENTATION` のビットを含むため）。
  全形式を `Unchanged` で読むと**スマホの縦写真が横倒しで出力される**。
  アルファを持ちうる形式（PNG / WebP / BMP、ファイル署名で判定）だけを
  `Unchanged` で読み、それ以外は `Color` で読むこと
- **`Unchanged` はビット深度も保持する。** 16bit PNG は `CV_16U` のまま返る。
  明るさの `Cv2.LUT` は 8bit 入力が前提なので、読み込み直後に 8bit へ落とすこと。
  この正規化は**アルファ合成より前**に行う（16bit のアルファは 0〜65535 のため）
- **アルファを保持する経路を作らないこと。** 4ch のままチェーンへ流すと、
  明るさの LUT がアルファチャンネルにも適用されて透明度が変わる。
  グレースケール・二値化・枠線も同様に方針が要る。変更する場合は
  **全調整項目のチャンネル方針を同時に決める**必要がある
## 出力を決める定数と、経路の一致

ここが崩れると、**同じ画像・同じ設定でも出力が変わる**。しかも UI に出ていない値が
多いので、外から見て変わったことが分からない。

- **プレビューの縮小サイズ（長辺 1600）は性能の調整値ではなく、出力を決める定数である。**
  二値化のしきい値は大津の方法で画像から決まるが、その計算は**この寸法に縮小した
  画像**に対して行う（プレビューと書き出しで同じ値を得るため）。したがって
  **この定数を変えると、同じ画像・同じ設定でも二値化の結果が変わる。**
  保存済みのプリセットを読み込んでも以前と違う絵が出る。性能調整のつもりで
  触らないこと。変更する場合は出力が変わることを承知のうえで行う。
  なお**プレビューの倍率は窓の大きさや DPI に依存させてはいけない**。
  依存させると、窓を広げただけで二値化の結果が変わる
- **シャープのぼかし半径（σ = 2.0）も、出力を決める定数である。**
  `CanonicalEdge` と同じ性質で、変えると同じ画像・同じ設定でもシャープの
  結果が変わり、保存済みのプリセットを読み込んでも以前と違う絵が出る。
  **しかも σ は UI に出していないので、外から見て変わったことが分からない。**
  調整のつもりで触らないこと。実装は `ImageRenderer.SharpenSigma`
  - **プレビューでは σ に倍率を掛ける**（`σ × previewScale`）。シャープはチェーンで
    唯一の空間フィルタで、1 画素だけを見る調整（明るさなど）と違い、画像の
    大きさに対する相対的な効きが結果を決める。掛けないと、縮小されたプレビューに
    原寸と同じ半径を掛けることになり、書き出しと違う絵になる（実測で平均差 16.3）
  - σ = 2.0 は、倍率を掛けた後も効きが残るように選んである。実測では σ が 0.3 を
    下回ると効果が消えるため、σ 2.0 なら倍率 0.15（長辺 10000px 程度）まで持つ
- **二値化のしきい値に渡す画素は、チェーンを「打ち切って」作る。設定を削った写しを
  流し直してはいけない。** `ResolveThreshold` には 2 つの経路がある。速い経路
  （プレビュー）はグレースケールまでを適用した画素をそのまま大津に渡し、遅い経路
  （書き出し）は canonical へ縮めてチェーンを流し直す。**この 2 つが同じ工程を
  たどることを、どう保証するかが問題になる**
  - **採る形**: `Apply` に `stopBeforeBinarize` を渡し、二値化の直前の `return` で
    打ち切る。「二値化の手前までのチェーン」の定義が 1 箇所しか無くなるので、
    順序が二値化より後ろの項目を足しても、それは打ち切りの `return` より下に
    書かれ、**しきい値の計算へ混ざりようがない**。縮小を `Downscale` 1 本に
    寄せたのと同じ形
  - **採らない形**: 設定の写しから二値化以降を落として `Apply` を流し直す。
    同じ「前半のチェーン」が 2 箇所に書かれ、片方を直し忘れると静かに食い違う。
    **実際にそうなっていた** — 束 3 でシャープ（順序 7）を足したとき写しから
    落とし忘れ、束 4 で枠線を足すまで気づかなかった（実測で 161 と 150）
  - 枠線はとくに悪い。塗り潰した帯をヒストグラムに混ぜるので、実測では
    白い枠線 40px を足しただけでしきい値が 126 から 152 へ動き、原寸の二値化で
    21.9% の画素が反転した
  - **残る失敗の形は「打ち切りの位置を間違える」だけ**で、これは
    `CheckThresholdAgreement` が 4 組全部で落ちる（実測。打ち切りをチェーンの
    最後へ動かすと 161 と 12 になる）。位置を間違えれば本流の適用順序も
    同時に変わるので、2 つの経路が食い違ったまま残ることはない
  - **標本を選び損ねると素通りする。**捕まえるには「後段が混ざるとしきい値が動く」
    ことと「動いた結果が実際に画素を反転させる」ことの両方が要り、この 2 つは逆を向く。
    明暗 2 領域の標本ではしきい値が 105 から 89 へ大きく動くのに、谷が広いので
    反転率は 0% だった。詳細は検証ハーネスの `WriteDetailed` の注記
  - **この不具合は束 3 で入り、既存の検証を 3 つとも素通りした。**
    捕まえるには (a) 二値化より後ろの項目が有効、(b) 原寸が `CanonicalEdge` 超、
    (c) プレビュー経路と書き出し経路の両方を通す、の 3 つが同時に要る。
    各テストは 2 つまでしか満たしていなかった

    | 検証 | (a) 後段 | (b) 原寸 | (c) 両経路 |
    |---|---|---|---|
    | `CheckThresholdAgreement`（束 2） | 二値化のみ | 4000×3000 ○ | ○ |
    | `TestSharpen` の「シャープは 1 画素も変えない」（束 3） | ○ | 320×240 | ○ |
    | `TestRenderEncodeAgreement` | ○ | 160×120 | 同じ source と倍率を両方に渡す |

    束 2 の時点では二値化より後ろに項目が無かったので、当時これは漏れではない。
    **項目を 1 つ足したことで、既にあったテストの前提が黙って崩れた**のが本質である。
    現在は `CheckThresholdAgreement` を 4 通りの組み合わせで回している。
    ただし**この種の網は「次に足す項目」を先回りできない**ので、テストではなく
    上の打ち切りの形で塞いでいる。テストは打ち切り位置を間違えたときの網として残す
  - **`context.PreviewScale == canonicalScale` による経路の分岐は `ResolveThreshold`
    の 1 箇所だけ**（確認済み）。他の `previewScale` の使い方はすべて連続な係数なので、
    「片方の経路だけ間違う」という同じ形にはならない
- **`Cv2.Resize` は、倍率で指定するか寸法で指定するかで結果が変わる。**
  倍率を渡すと `dsize = round(src × fx)`、寸法を渡すと `fx = dsize / src` を
  内部で求めるため、割り切れない比では係数が食い違う。実測では同じ寸法に
  なっても**最大 30 階調・全体の 54% の画素が違った**（2551×1699 を長辺 1600 へ）。
  **同じ画像を作るつもりの縮小は、必ず同じ 1 つの関数を通すこと。**
  呼び出し箇所を分けた時点で「同じ入力に同じ処理だから一致する」という
  説明は成り立たなくなる
## WPF と Win32

- **Win32 の API は物理ピクセルで、WPF のプロパティは論理ピクセルである。**
  `MoveWindow` や `SetWindowPos` に XAML と同じ数値を渡すと、高 DPI の環境では
  要求より小さい窓になる。論理ピクセルで指定したいときは
  `GetDpiForWindow(hwnd) / 96.0` を掛けること。
  実際、150% の環境で `MoveWindow` に 1000×720 を渡したところ 667×480 相当になり、
  `MinWidth` / `MinHeight`（720×600）に丸められて、**既定サイズのつもりで
  最小サイズを撮っていた**。窓が小さくなるだけなので気づきにくく、
  既定サイズでしか出ない不具合（スクロールバーとスピンボタンの重なり）を
  長い間見落とした。実装は `tools/screenshot.ps1`
  - なお **WPF の `Window.Width` / `Height` は論理ピクセル**なので、倍率を掛けては
    いけない。同じ「幅」でも API によって単位が違う
- **ウィンドウの画像を取るのに `Graphics.CopyFromScreen` を使わない。**
  これは「いま画面に映っているもの」を取るため、画面が描画されていない状態
  （ロック中・リモート切断・省電力での消灯・他ウィンドウでの遮蔽）では
  **白紙が返る**。実際にそれが起き、変更による回帰かどうかの切り分けに時間を使った。
  `PrintWindow` に `PW_RENDERFULLCONTENT`（`0x2`）を渡すと、DWM にウィンドウの
  中身を描き直させるので画面の状態に依存しない。枠は `GetWindowRect` ではなく
  `DwmGetWindowAttribute(DWMWA_EXTENDED_FRAME_BOUNDS)` で取ること
  （前者は影のぶん大きい）。実装は `tools/screenshot.ps1`
- **`ColumnDefinition.MaxWidth` は測定を制限しない。** 列に付けても
  `TextTrimming` が働かず、文字が省略されずに単に切れる。上限は
  **`TextBlock` 側に付ける**こと。固定値にすると窓を広げても省略が
  解けないので、行の幅に対する割合で決める（`WidthFractionConverter`）
