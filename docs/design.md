# 設計と仕様

## 設計方針

### 非破壊の処理チェーン

画像に直接書き込むのではなく、**「何をどれだけかけるか」の設定値のみを保持し、表示のたびに元画像から作り直す**。

- 元画像は一切変更しない（画質劣化が蓄積しない）
- 後からの再編集・Undo・プリセット化がすべて同じ仕組みで実現できる

### 適用順序は固定

順序をユーザーが入れ替えられるようにはしない（実装も理解も難しくなり、「分かりやすさ」の目的に反する）。以下の順で固定する。

1. 回転
2. リサイズ
3. 明るさ / コントラスト（LUT で一括適用）
4. 彩度
5. グレースケール
6. 二値化（大津の二値化）
7. シャープ
8. 枠線

順序の根拠:
- **リサイズを先に**行うことで以降の処理コストが下がる
- **シャープはリサイズ後**に。効きが解像度に依存するため
- **枠線は最後**。先に付けるとリサイズで線の太さが崩れる

明るさとコントラストは**同じ 1 本の LUT にまとめて 1 回で通す**（別々に通すと中間の丸めが 2 度入る）。LUT の中では**コントラストが先、明るさが後**。逆にすると明るさの効きがコントラストの倍率だけ増減し、「コントラストを上げたら明るさスライダーの効き方まで変わった」という挙動になる。

コントラストの倍率は **`2^(c/100)`**（-100 で 0.5 倍、0 で 1 倍、+100 で 2 倍）。`1 + c/100` にすると -100 が 0 倍になり、一面が中間の明るさに潰れて画像の情報が消える。実写で確かめたところ -50 の時点で既にかなり平坦で、**スライダーの下半分の大部分が実用にならない領域**になっていた。倍率で対称にすると全域が使える。

### 設定モデル

項目数が固定・順序も固定であるため、多態なリスト（`List<IAdjustment>`）ではなく、**全項目を持つ単一の設定クラスとし、各項目に `Enabled` フラグを持たせる**。`System.Text.Json` のポリモーフィックシリアライズが不要になり、単純に扱える。

実物は `Models/ProcessingSettings.cs` と各 `*Option.cs`。**新しい項目を足すときは `BrightnessOption` を写して作る**（Enabled、上下限の定数、`Clone` への追加まで一式そろっている）。

`SchemaVersion` は初版から必ず入れる。後から項目を変更したときに古いプリセットを分岐処理できる。

#### 値の範囲は Option 側で丸める（必須）

範囲を持つ値（明るさ、リサイズの寸法、シャープの強さ、枠線の太さなど）は、**上下限の定数を Option クラスに定義し、setter で `Math.Clamp` して丸める**。

View 側だけで丸めてはいけない。**依存関係プロパティの `CoerceValue` による丸めは、TwoWay バインディングのソースまで伝わらない**（WPF の仕様）。View で丸めたつもりでも設定値は範囲外のままになり、画面には 100 と表示されているのに実際は 1000 で処理される、という表示と結果の食い違いが起きる。プレビューと書き出しの一致が最大の差別化ポイントである以上、ここは必ずデータ側で保証する。

上下限の定数は XAML からも参照し、スライダーと数値入力の範囲を 1 箇所で定義する。ただし `Slider.Minimum` は `double` であり **`x:Static` は型変換をしない**ため、`int` の定数を直接渡すと実行時に落ちる。`{Binding Source={x:Static ...}, Mode=OneTime}` と書けば変換が効く。

### プレビューとレンダリング

- **プレビュー**: 縮小した画像に対してチェーンを適用し、リアルタイムに反映
- **書き出し**: フル解像度で再計算

「処理してみないと結果が分からない」既存ソフトに対する最大の差別化ポイント。ここは体験の質に直結するので手を抜かない。

## 機能仕様

### 入力

ドロップとフォルダ選択の**モード切替は設けない**。どちらも同一のファイルリスト（`ObservableCollection<ImageItem>`）に追加する手段にすぎない。

- ドラッグ＆ドロップでファイル追加
- 「フォルダから追加」ボタンで `Directory.EnumerateFiles` により列挙して追加
- 対象拡張子: `.jpg` `.jpeg` `.png` `.bmp` `.webp`
- **サブフォルダは含めない**（初版）。含める場合は出力時のフォルダ構造再現の判断が発生するため
- パスによる重複除外（同じフォルダを 2 回追加しても二重処理しない）
- 表示順は、**追加したバッチごとにエクスプローラーと同じ自然順（`StrCmpLogicalW`）でソートし、末尾に追加**した結果。`Directory.EnumerateFiles` の順序も、ドロップ時に OS が渡す順序も保証されないため。**リスト全体の再ソートはしない**（追加分が中程に紛れ、追加できたか分からなくなる）。連番リネームはこの順に従う

### 調整項目

上記「適用順序は固定」の 8 項目。既定は**全項目 OFF**、ユーザーが触ったものだけ有効化する。

**9 項目すべて実装済み。**

**「彩度 -100」と「グレースケール ON」は全画素一致する**（検証済み。ハーネスに常設）。彩度を HSV でも Lab でもなく**輝度（`BGR2GRAY`）との線形補間**で実装した根拠がここにある。崩すと「彩度 -100」と「グレースケール ON」で違う絵が出る。

**グレースケールと二値化の相互作用**
- 二値化はそれ自体が輝度へ落とすため、**二値化が ON ならグレースケールの ON / OFF は結果を変えない**（`BGR2GRAY` は既にグレーの画像に対して冪等。全画素一致を検証済み）
- **設定を自動で切り替えたり排他にしたりはしない。** どちらも「触っていない設定が勝手に変わる」形で、サフィックス自動 ON を却下したのと同じ理由で採らない。**吸収するだけで、設定は動かさない**
- 分かりにくさは文字で断る（「グレースケールと同時に有効でも結果は変わりません」）。既定の路線に合わせ、状態に依存しない常時表示にする
- **彩度は吸収されない。グレースケールと同じ形に見えるが別物である。**
  - グレースケールの吸収は**厳密**（全画素一致を検証済み）。倍率 0 の補間なので飽和しない
  - 彩度は `out = 元 × k + グレー × (1-k)`。**k > 1（彩度を上げる方向）では `AddWeighted` が 0 / 255 で飽和し、輝度が実際に変わる**。実測で二値化の結果が 4.755% の画素で変わった。k ≤ 1（下げる方向）は飽和しないので 0.036%（8bit の丸めのみ）
  - したがって**「彩度 → グレースケール」は「グレースケールのみ」と同じ結果にならない**。順序が固定である以上これは仕様であって不具合ではない
  - **「後段が前段を上書きするから彩度は無視できる」と判断して最適化を入れないこと。** 静かに結果が変わる

**シャープ**

- 方式は**アンシャープマスク**（`元 + 量 ×（元 − ぼかし）`）。ラプラシアンの 3×3 加算は**採らない**。半径が 1px に固定され、プレビューの倍率に合わせて縮められないため、プレビューと書き出しで違う絵になる。**噛み合わせの問題が方式選択を決めている**
- 半径（σ）は UI に出さず固定。2 本目のスライダーを出すほどの価値がない（詳細は [pitfalls.md](pitfalls.md)）
- **二値化 ON のときシャープは 1 画素も変えない。** 0 と 255 しかない画像では、明るい画素は 255 を超え、暗い画素は 0 を下回り、いずれも飽和で元の値に戻る。実測で 3600 万要素すべてが不変だった。**「ほぼ効かない」ではなく厳密にゼロ**
  - 設定は自動で切り替えず、文字で断る（グレースケール・二値化のときと同じ）
- **縮小表示のプレビューでは効果が分かりにくい場面がある。** 倍率が小さいと σ も小さくなり、σ 0.3 を下回ると効果が消える。ただしその倍率では書き出しをプレビューの大きさで見ても効果は見えないので、**プレビューは嘘をついていない**。原寸で開けば見える、という食い違いは縮小表示に固有の制約であり、方式を変えたり近似で誤魔化したりはせず文字で断る

**既知の限界: シャープを有効にすると、プレビューと書き出しは画素単位では一致しない**

テストが通ることと現象が無いことは別である。**「一致は保証されている」と読まないこと。**

- 実測 2026-08-10（実写 3000×4000、リサイズ 1280、コントラスト 100、彩度 100、シャープ 100、倍率 0.40）で**平均差 5.224 / 最大差 115**。ハーネスの標本では通るが、現象そのものは残っている
- **目で見て分かるかは確認済み。分からない。** 同じ設定でプレビューと書き出し（プレビュー寸法へ縮小）を並べて比較したところ、構造の違いは無く、差はテクスチャ部分の粒状のばらつきだった。3 倍に拡大すると粒の出方が違うと分かる程度。差だけを 8 倍に強調すると、細部のある領域一面に散らばった雑音として見える
- **原因は原理的なもので、直せない。** プレビューは「縮小 → シャープ」、書き出しは「シャープ → （見るときに）縮小」で、この 2 つは交換できない。縮小で失われた高周波は、縮小後にシャープをかけても戻らない。逆に原寸でシャープした細部は、縮小の平均化でならされる。**極端なコントラストと彩度（各 2 倍）がこの画素差をさらに約 4 倍に増幅する**ため、シャープ単独の 0.9 から 5.2 に跳ね上がる
- **大津のように「共有の計算で揃える」手は使えない。** 二値化で揃えられたのは、経路で食い違うものが**しきい値というスカラー 1 個**だったから。シャープで食い違うのは**画素データそのもの**であり、共有できる代表値が無い。完全に一致させる唯一の方法はプレビューを原寸の結果から作ること（原寸チェーン → 縮小）だが、それはプレビューを縮小画像で作るという設計の目的そのものを捨てることになる

**二値化のしきい値**
- **大津の方法で自動決定し、UI には出さない。** 一括処理では多様な画像が混ざるため、手で決めた 1 つの値は多くの画像で外れる。プレビューは選択中の 1 枚だけなので、手で合わせるとその 1 枚に最適で他は黙って外れる
- 明るさやコントラストで実質的にずらすことは**できない**。明るさを +N すると大津の求める値もほぼ +N ずれるため結果はほとんど変わらない。ずらす手段が要ると分かったら、大津の値に対するオフセットを 1 つ足せばよい（加算式に足せる）
- **しきい値は `ImageRenderer.CanonicalEdge` に縮小した画像から求める**（プレビューと書き出しで同じ値にするため。詳細は [pitfalls.md](pitfalls.md)）。代償として、しきい値は原寸ではなく縮小画像から決まる。原寸の大津のほうが良い値を出す場面はありうるが、**ユーザーが見て納得したのは縮小画像から決まった値のほう**である
- 書き出しの増分は**十数 ms 程度**（`--bench` の「二値化の増分」で測れる）。原寸が `CanonicalEdge` 以下の画像では縮小もチェーンの流し直しも走らない（`ScaleFor` が 1.0 を返し、書き出しの倍率も 1.0 なので最初の分岐で戻る）
- **しきい値に使う画素は `Apply` を `stopBeforeBinarize` で打ち切って作る。** 設定から二値化以降を落とした写しを流し直す作りにはしない。写しを作ると「二値化の手前までのチェーン」が 2 箇所に書かれることになり、後ろに項目を足したとき落とし忘れると静かに食い違う。詳細は [pitfalls.md](pitfalls.md)

**回転**

- **90 度単位のみ（右に 90° / 180° / 左に 90°）。任意角度は入れない。** 決め手は補間や余白の色ではなく、**任意角度が一括処理と噛み合わない**こと。傾き補正の角度は 1 枚ずつ見ないと決められないもので、同じ 2.3 度を 200 枚にかければ 199 枚が傾く。全件に同じ値をかけるという前提で意味を持つのは 90 度単位だけである
- 副次的に、`Cv2.Rotate` は転置と反転だけなので補間による画素の変化がなく、余白も出ず、寸法は縦横が入れ替わるだけになる
- **「回転しない」は列挙に持たせず `Enabled` で表す。** 0 度を足すと「回転しない」の言い方が 2 つできる
- **適用順序 1 番目なので、以降の全項目が回転後の画像を前提にする。** リサイズ（長辺は回転で不変）・大津のしきい値（ヒストグラムは並べ替えで不変）・シャープ（ガウシアンは等方）・枠線（4 辺に一様）はいずれも噛み合う。**チェーン全体が 90 度回転と可換であることをハーネスに常設してある**（「回転 → 全チェーン」と「全チェーン → 回転」の全画素一致、3 角度とも成立を実測）。後から他の項目を触ったときの網になる
- **寸法表示は回転後で計算する。** 90 度回すと縦横が入れ替わるので、回転前の寸法にリサイズを掛けた値は実際の出力と食い違う

**枠線**

- **画像の内側に描く。外側には足さない。** 外側に足すと出力寸法が変わり、長辺 1920 を指定したのに 1960 になる。1920 を選ぶのはたいてい上限がある先へ渡すためで、それが黙って破れるのは、写真の外周が数画素隠れるのとは質の違う失敗である。構造の面でも、枠線は順序 8 でリサイズ（順序 2）より後にあるため、外側に足すと**最後の工程が先の工程の約束を取り消す**ことになる
- **太さは出力画素の px で固定する。比率にはしない。**
  - 短辺比率は逆効果。リサイズ後にアスペクト比の違う画像が混ざると揃わない（長辺 1920 に揃えても 1920×1440 と 1920×1080 では短辺が 1440 と 1080 で 1.33 倍違う）
  - 長辺比率ならそれは起きない。px 固定と差が出るのは**出力寸法がバラバラなバッチ**で、そこでは**出力寸法自体が揃っていない**のだから、枠線だけを相対的に揃えても並べたときに揃って見えるわけではない。数値が結果そのものになる px を採る
  - **この根拠の射程は当初の想定より狭い。** 束 4 の時点では「差が出るのはリサイズ無効のときだけ」と書いていたが、**リサイズは拡大しないので、有効にしても指定より小さい画像は元の寸法のまま出る。** 小さい画像が混ざったバッチは、リサイズを有効にしても出力寸法が揃わない（実測: 長辺 1920 で `4000×3000 → 1920×1440` と `120×90 → 120×90` が同居する）。**結論は変わらない** — 長辺比率にしても 120×90 の枠線が 2px になるだけで、太さの不揃いが別の形に置き換わるだけである
  - プレビューでは倍率を掛ける（シャープと同じ）。倍率を掛けた結果が 0 になっても 1px は描く。プレビューだけ枠線が消えると嘘になる
- **色は白 / 黒 / グレーの 3 択、既定は白。** 固定は無理（白背景なら黒枠、暗い背景なら白枠と用途で必ず変わる）。かといってフルカラーのピッカーは、一括処理でその自由度が要る度合いに対して UI が重すぎる（ピッカーのダイアログ、16 進の入力、プリセットへの保存形式）。既定を白にするのは透過の合成色と揃えるため。任意色が要ると分かったら列挙に値を足すか ARGB へ移す（`SchemaVersion` があるので移行できる）
- **太さは出力の短辺の 1/4 で頭打ちにする**（`FrameOption.ShortEdgeDivisor`）。内側に描く以上、太さが画像を食い尽くしうる。**この頭打ちは黙って効かせない** — 選択中の 1 枚については寸法表示の行に出し（`4000 × 3000  →  1920 × 1440　枠線 40px（上限）`）、全件については書き出しの結果に件数を出す（後述）
- **出力寸法の求め方は `ProcessingSettings.ResolveOutputSize` の 1 本に閉じる。** 寸法表示・チェーンの適用・頭打ち判定がそれぞれ「回転してからリサイズ」を書き写していると、片方だけ直したときに表示と結果が食い違う。二値化のしきい値で同じ形の食い違いを起こしたので、こちらは最初から 1 本にしてある
- **太さは枠線が有効な間は常に出し、上限に当たったときだけ `（上限）` を添える。** 上限のときだけ出す形にすると、出ていない状態が「指定どおり」なのか「表示の条件を満たしていない」のか区別できない。常に出ていれば「40px と指定して 40px と表示される」状態が基準になる

**全件の内訳は書き出し後に出す。書き出し前には出せない**

一括処理では画像ごとに短辺が違うので、**選択中の 1 枚が上限内でも、他の画像では頭打ちに当たっていることがある。**プレビューが 1 枚しか映さないことに起因する制約で、二値化のしきい値が選択中の 1 枚からしか確かめられないのと同じ形である。

**揃うのは「小さい画像が混ざらないバッチ」に限る。** かつてここには「リサイズを有効にすれば出力寸法が揃うので、当たるか当たらないかが全件で一致する」と書いてあったが、**これは誤りだった。リサイズは拡大しないので、指定より小さい画像は元の寸法のまま出る。** 実測（長辺 1920・太さ 30px・9 件）で、`4000×3000 → 1920×1440` の画像が上限に当たらない一方、`120×90` の画像だけが 22px に頭打ちしていた。リサイズは緩和条件にならない。

緩和条件が無い以上、全件の内訳を出す手段が要る。**書き出しの結果に件数を載せる**（`ExportResult.FrameCapped`）。

```
9 件を書き出しました。1 件は画像が小さく、枠線が指定より細くなりました
```

書き出しは全件を開くので、そこで数えるぶんには費用がかからない。判定は `ProcessingSettings.IsFrameCapped` の 1 本を通り、寸法表示と同じ計算になる。

**書き出し前の見積もりには出さない。** 却下の理由は「全画像を開くと費用が跳ね上がる」ではない — それは**展開**の話で、寸法だけならヘッダで足りる（実測 2026-08-14、211 枚 290MB の JPEG に対し、WIC のヘッダ読みが 9ms / 1 枚 0.04ms、`ImDecode` が 1 枚 17.5ms）。**採らない理由は WebP である。** WIC で WebP を読むには Windows のコーデック拡張が要り、zip 解凍で配る以上それが入っていない環境がありうる。そこでは WebP だけが黙って数から漏れる。**間違った件数を出すくらいなら出さない。** 自前でヘッダを解析すれば依存は消えるが、形式ごとの解析を持つ費用に対して、得られるのは「1 回の書き出しを待たずに済む」ことだけで、しかもこれは原則 2 に関わらない可逆な設定である。

- なお**頭打ちの判定は元画像の縦横がどちらでも同じ答えになる**（短辺は 90 度回転で不変、リサイズは縦横を同じ係数で縮める）。Exif の Orientation が効いているかどうかを気にせず判定できるので、**もし将来ヘッダ読みを入れるなら、この点は障害にならない**。ハーネスに常設してある

調整パネルは項目が増えると縦に伸びる。**項目を足すたびに既定サイズで全項目が見えるかを測り直すこと**（測り方は「既定ウィンドウサイズ」）。

UI では以下の 3 分類でパネルを区切る（項目数が多くても圧迫感を出さないため）。

| 種別 | 項目 |
|---|---|
| キャンバスを変える | 回転、リサイズ |
| 画素値を変える | 明るさ、コントラスト、彩度、グレースケール、二値化、シャープ |
| 描き足す | 枠線 |

### 出力

**出力先**
- 既定は**別フォルダ**への出力（起動直後は未設定）
- 同フォルダへの出力も選べる。ただし出力先が元ファイルと一致した 1 枚は安全ガードで必ずスキップする（後述）
- **上書きは提供する。ただし既定はオフ**で、実行前に件数を警告色で明示する（後述「同名ファイルが既に存在する場合」「安全ガード（必須）」）

**形式**
- `.jpg` / `.png` / `.bmp` / `.webp`、および「**元の形式を維持**」
- JPEG: `JpegQuality` 0〜100（既定 95）を UI に出す
- WebP: `WebPQuality` 1〜100（既定 95）。**可逆はチェックボックスで指定する**。OpenCV は 101 を渡すと可逆になるが、この数字は知らなければ意味が分からないため数値入力にはせず、変換は `ExportSettings` の中に閉じる
- PNG: `PngCompression` は**可逆で画質が変わらない**ため UI に出さず固定値（**4**）。「画質」と表示すると誤解を招く
  - **値は実測で決めた。慣習（一般的なツールの既定が 6）を根拠にしない。** その慣習は 1 枚単位の話で、一括処理では枚数倍に効く
  - 以下は `--bench` の出力そのもの。実測 2026-08-10（Release、Intel Core Ultra 5 245K、Windows 11、7 回測って最初の 2 回を捨て残り 5 回の中央値、エンコードのみ）。
    再現は `dotnet run --project tests/Soroe.Verify -c Release -- --bench 写真.jpg`。
    **別の環境では絶対値ではなく比率で見ること**（1 → 4 が約 1.5 倍、4 → 6 が約 3 倍）

    | 圧縮率 | 実写 3000×4000 | 平坦 3000×4000 | 平坦 1500×1080 |
    |---:|---|---|---|
    | 1（OpenCV 既定） | 508ms / 16.30MB | 117ms / 180.9KB | 16ms / 26.8KB |
    | 3 | 834ms / 15.67MB | 120ms / 180.9KB | 16ms / 26.8KB |
    | **4（現在）** | **758ms / 16.07MB** | **173ms / 93.0KB** | **23ms / 13.9KB** |
    | 6 | 2253ms / 15.25MB | 174ms / 51.3KB | 24ms / 8.5KB |
    | 9 | 5132ms / 14.92MB | 203ms / 51.0KB | 33ms / 8.5KB |

  - **費用と便益が別の画像に乗っている。** 実写は PNG ではほとんど縮まないのに時間だけ延びる。平坦な画像はほとんど時間をかけずに大きく縮む。211 枚が全部実写なら、6 は 1 に対して **6 分 15 秒**を余分に使ってサイズを 6.5% 減らすだけ
  - **4 と 6 のどちらにするかの決め手は、上の表ではなく実際のスクリーンショットで測った値だった。** 実物（1500×1080 のこのアプリの画面）では 4 が 76.8KB、6 が 75.8KB で差がほぼ無い。一方、上の表の「平坦」は合成標本で、規則的な繰り返しが多いぶん **6 の利得を過大に見せる**（13.9KB → 8.5KB）。合成の写真が逆に圧縮率の差を過小に見せるのと対になっている。**判断をやり直すときは、写真も平坦も実物を使うこと**
  - **`WebPQuality` は今回の対象外。** WebP は 1 枚 1.8 秒かかるが、これは圧縮率の設定ではなく**エンコーダ自体の費用**で、PNG の圧縮率を下げても速くならない
- BMP: 設定なし

**透過（アルファチャンネル）**
- **保持しない。透明部分は白で合成する。** 出力形式によらず挙動は同じ
- 出力形式による分岐（PNG なら保持、JPEG なら合成）は**採らない**。アルファを保持する経路が生まれると、全調整項目にチャンネル方針が必要になるため
- 合成は**読み込み直後**に行い、チェーン以降は常に 8bit 3ch として扱う。合成は `Load` の中の 1 箇所だけで、プレビューも書き出しもその同じ関数を通るので、**ここは実装が 1 本しかないという意味で構造的に保証される**（二値化のしきい値の一致とは違う。あちらは 2 つの経路を手で揃えている。[pitfalls.md](pitfalls.md) 参照）
- 調整は合成後の画素にかかる。暗くする調整をかければ、元・透明だった部分も一緒に暗くなる

**Exif**
- **常に削除される。選択の UI は設けない。** `Cv2.ImEncode` が Exif を書き出さないため削除が既定の挙動であり、実装が必要なのは「残す」ほう。選択式にすると「残す」を選べてしまうので、選択肢自体を出さない

**ファイル名**
- 3 択にする。既定は「そのまま」（元ファイルとの対応が追える）
  - **そのまま** … `IMG_0001.jpg`
  - **前後に文字を足す** … プレフィックス / サフィックス
  - **連番で付け直す** … `photo_001.jpg`
- 連番の順序は**リスト表示順に固定**し、その旨を UI に明記する（表示順の決め方は「入力」を参照）。撮影日時順は Exif 読み取りが必要なため初版では行わない
- 連番の細部は**選ばせない**（桁数・開始番号・拡張子・区切り。根拠は `OutputPathResolver.cs`）。ベース名だけは空を許す — 「番号だけ」という要求は普通にあるため
- プレフィックス / サフィックス / ベース名は、**値の setter で使えない文字を取り除く**（`Math.Clamp` と同じ考え方。View 側だけで弾くとバインディングのソースまで伝わらない）

**同名ファイルが既に存在する場合**
- **チェックボックス 1 つだけにする。** 既定はオフ
  - オフ … 別名で保存する（`IMG_0001 (2).jpg`）。エクスプローラーのコピーと同じ挙動
  - オン … 上書きする
- **「スキップ」は設けない。** 中断からの再開に便利という理由はあったが、上書きでも結果は同じで違うのは処理時間だけである。正しさの機能ではなく速度の最適化なので、分かりやすさを優先して落とす。必要になれば後から足せる
- 別名の付け方（括弧か桁数か）は**ユーザーに選ばせない**。`(2) (3)` と自動で付けるのみ
- **同じ実行の中で書いたファイルは、上書きが選ばれていても決して上書きしない。** 複数フォルダから同名ファイルを追加してプレフィックスのみを付けると出力先が衝突するが、そこで直前に書いた成果物を潰してはいけない。`File.Exists` では「前回の実行結果」と「今回書いたファイル」を区別できないため、実行中に使ったパスを別に記録して避ける
- 上書きが選ばれているときは、**実行前に件数を警告色で明示する**（`うち 3 件を上書きします`）。これが原則 2 に対する最後の確認になる

**書き出しダイアログ**
- **設定・実行・進捗・結果・失敗一覧をすべてダイアログの中で完結させる。** 押した場所と結果が出る場所が違うと操作として不自然になるため。書き出しは「ついでの操作」ではなく主目的の作業である
- 出力に関する設定（出力先・形式・品質・ファイル名・衝突時の扱い）は**すべてこのダイアログの中**に置く。主画面には結果の 1 行と「書き出し...」ボタンだけを残す
- 主画面のボタンは「実行」ではなく **`書き出し...`**。押しても即座には書き出さず、まずダイアログが開く（三点リーダーがその意味を表す慣習）。実際に書き出すのはダイアログの「実行」
- **主画面のボタンの有効条件に出力先を入れてはいけない。** 出力先を設定する場所がダイアログの中なので、条件に入れると設定するためのダイアログを開けなくなる。条件は「画像が 1 件以上ある」。出力先が必須であるという判定はダイアログ側の実行ボタンが持つ
- ダイアログを閉じても**設定は破棄しない**。出力先を選び直してから「やはり後で」と閉じたときに消えるのは煩わしいため。ボタンの文言も「キャンセル」ではなく **`閉じる`** にして、語と挙動を一致させる
- **モーダルで開く。** 書き出し中に主画面を触れないことは制限ではなく利点として扱う。「いま触ってよいのか分からない」という曖昧さが無くなり、実行中の個別の無効化処理とその漏れも不要になる。ダイアログの移動・アプリの最小化・他アプリへの切り替えは妨げられない
- 完了しても**自動で閉じない**。結果と失敗一覧を残し、`閉じる` で消す
- 実行中もサイズ変更を許可し、「実行」自体は無効化して二重実行を防ぐ
- **中止できることが生命線。** 主画面が触れない以上、止める手段はダイアログのキャンセルだけになる。1 枚ごとに合図を確認し、押してから長くても 1 枚分で止まること
  - **その「1 枚分」は形式で大きく変わる。** 実測 2026-08-10（Release、実写 3000×4000、読み込みから書き込みまで）で JPEG 80ms / BMP 85ms に対し、**PNG 0.8 秒 / WebP 1.8 秒**。WebP では中止に 2 秒近くかかりうる。エンコードの途中で割り込む作りにすると中途半端なファイルの後始末が要るため、1 枚を区切りにする形は変えない。再現は `--bench`（[../AGENTS.md](../AGENTS.md) の「構成とビルド」参照）
- 書き出し中にダイアログの × を押した場合も、中止を要求して 1 枚分の終了を待ってから閉じる（中途半端な一時ファイルを残さないため）

**安全ガード（必須）**
- 出力先の絶対パスが**リスト内のいずれかの入力ファイルのパス**と一致した場合、**その 1 枚は無条件でスキップする**。ユーザーが出力先に元フォルダを指定したときに原本が消える唯一の致命的シナリオを塞ぐ
  - **比較対象は「そのファイル自身」ではなく「リスト内の全入力パス」。** 例えば `IMG_0001.jpg` と `小_IMG_0001.jpg` が同じリストにあり、同フォルダ出力・プレフィックス `小_`・上書き ON だと、前者の処理結果が後者（別の原本）を潰す。自分自身とだけ比べる実装ではこの経路が残る
- **全件がスキップされる設定では実行させない。** 押しても 1 枚も書き出されず「壊れている」という印象になる。設定を直す場所はダイアログの中にあるので、無効にしても手詰まりにはならない。ただし**一部だけのスキップでは無効にしない**（残りは正しく書き出される、正当な実行のため）
- **「同フォルダ出力ならサフィックスを自動 ON」は採らない。** 出力先を選んだだけでファイル名の設定が勝手に変わるのは「設定は自分が変えたものだけが変わる」という期待に反する。加えて発動するのが「出力先を選んだ瞬間」だけなので、先に出力先を選んでから画像を追加した場合には働かない。見積もりによる警告は操作の順序に関わらず正しく出るため、そちらに一本化する
- 出力パスのプレビューを 1 行表示する。**主画面（書き出しボタンの上）とダイアログの両方**に出す
  例: `C:\output\IMG_0001.jpg`（12 件を処理）＋ `うち 3 件を上書きします`
- **件数の見積もりは書き出しと同じ解決処理で計算する**（`ExportPlan`）。別の計算で数えると表示と結果がずれる
  - 上書きがオフなら、既存ファイルは必ず避けられるので上書き件数もスキップ件数も必ず 0 になる。全件を調べる必要がない
  - 上書きがオンのときだけ全件に `File.Exists` が走るため、少し待ってからバックグラウンドで計算し、新しい要求が来たら古い結果は捨てる
  - **実行を押した時点で見積もりを確定させる。** 表示していた件数と食い違い、かつ確認が要る内容（上書きあり・全件スキップ）を含む場合は実行せず、読み直してもらう。古い確認に基づいて上書きを実行してはいけない
- **見積もりと結果は排他にする。** 見積もりは「今の設定でもう一度押したらこうなる」という予告であって、直前の実行結果ではない。並べると結果の報告と読み違える。実行前は見積もりのみ、実行後は結果のみ、設定を変えたら結果を消して見積もりに戻す
- **実行前の再確認は「見積もりが画面に出ているかどうか」を根拠にしている**（`ShowEstimate ? _plan : null`）。結果を出している間は見積もりを隠しているため、その状態で実行を押されたら「予告を見せていない」とみなして一旦止める。これが無いと、書き出し後にもう一度押しただけで、上書き件数を一度も見せないまま実行されてしまう
  - **したがって表示状態と安全判定が結合している。** 表示まわり（`ShowEstimate` の意味、見積もりの出し分け、ダイアログのレイアウト）を変更するときは、**必ず再確認の挙動もあわせて確認すること**。レイアウトの都合で `ShowEstimate` の意味がずれると、安全側の挙動が静かに変わる

**エラーの見せ方**
- .NET の例外メッセージを**そのまま画面に出さない**。英文が日本語 UI に混ざるうえ、一般の利用者には何を直せばよいか伝わらない。`FileErrorMessage.Describe` で日本語の短い文に対応付ける
- ただし**原文は捨てない**。デバッグ出力へ流し、失敗一覧は原文込みでクリップボードにコピーできるようにする。不具合の報告を受けたときに原因を絞るため
- 原因を断定できないものは断定しない。例えば `ArgumentException` は発生源が広いため、実際に不正な文字が含まれる場合に限って「パスに使えない文字」と表示し、それ以外は汎用の文言に落とす

### プリセット

- 形式: JSON
- 保存先: **exe と同じ場所**（zip 解凍で動く可搬性を重視。`%AppData%` は使わない）。名前付きプリセットは `presets` フォルダに置く
- **終了時に現在の設定を自動保存し、起動時に復元**する（UI 不要でありながら体感価値が最も大きい）。**実装済みはここまで**

**名前付きプリセットは公開後の要望待ち（未実装）**

構想は「上部に 1 行 `[プリセット ▼] [保存] [削除]`。ドロップダウンで選ぶと即適用、保存は名前を尋ねるダイアログ 1 つ」。ただし**初版には入れない。要望が出てから着手する。**

- **自動保存・復元で体感価値の大半が得られている。** 前回の設定がそのまま戻るので、同じ用途を繰り返すだけなら名前付きプリセットは要らない
- **出力先ごとの使い分け（「ブログ用 1920」と「SNS 用 800」のような行き来）が実際に発生するかは、公開して使われてみないと分からない。** 作者が手元で一通り使った時点では、設定を行き来する場面が想定できなかった。想定だけで UI を足すと、**上部に常時 1 行を占有する代償だけが確定する**（縦を空けるためにダイアログへ切り出したのと逆方向になる）

なお `presets` フォルダと `settings.json` を分ける方針は既に決めてあるので、着手するときに保存先を作り直す必要はない。

**自動保存（`settings.json`）**
- ファイル名は `settings.json` とし、**`presets` フォルダの外**に置く。中に入れると `settings` という名前のプリセットと衝突する。「前回の状態」と「名前を付けて残したもの」は別物である
- **`Overwrite` は保存しない。起動時は必ずオフになる。** 前回オンにしたまま忘れると、次の実行で気づかないうちに上書きが走る。他の設定と違って取り返しがつかない（原則 2）
  - 除外は「たまたま書き忘れた」ではなく「意図的に除外した」と分かる形にする。**除外プロパティを明示的なリストとして持ち、理由をコメントで残す**
  - リストは**保存時と復元時の両方**に適用する。片方だけだと、古い設定ファイルが残っている環境や手で書き換えたファイルから値が復活する
- ルートに `schemaVersion` を持つ。**「未知なら既定値」の判定は「現在より新しい版なら既定値」という意味**で実装する。古い版は捨てるのではなく将来の移行の対象になる
- 保存するのは**設定値だけ**。リサイズの「自由入力かどうか」のような入力方法の選択は保存せず、復元した値から導出する
- 出力先は存在しなくてもそのまま復元する（USB メモリやネットワーク共有は次の起動時に無いことがある）。**ただし存在確認を同期の経路でやらない。** 応答しないドライブではタイムアウトまで数秒戻らない。既存の非同期の見積もり（遅延 + バックグラウンド + 最新優先）の中で行い、ダイアログの注意書きとして出す。繋ぎ直せば解消するので実行は止めない
- **読み書きのどんな失敗もアプリを止めない。** 読めなければ既定値で起動し、保存に失敗しても終了を妨げない。原因はデバッグ出力に残す

**保存の作法**（背景と実測値は `SettingsStore.cs` / `SettingsAutoSaver.cs` のコメント）

- **「変更から数秒後（デバウンス）」と「終了時」の二重で行う。** `Application.OnExit` はクラッシュ・強制終了・シャットダウンでは呼ばれない
- **保存対象のプロパティは、変更したら必ず変更通知を上げること。** 通知を上げない保存対象を 1 つ作るだけで「変更しても保存されない」項目になり、しかも値の往復を見るテストは通ったままになる。リフレクションで全項目を 1 つずつ変更して確認する（`Clone` の完全性検証と同じ考え方）
- **一時ファイルに書いてから `File.Move(overwrite: true)` で置き換える**（書き出しと同じ手法）。**名前にはプロセス ID を入れる** — 多重起動で 2 つのプロセスが同じ一時ファイルを使うと、挟んだ意味が無くなる
- 置き換え先は 1 つしかないので取り合いは残る。**数回の再試行で吸収する。このとき `UnauthorizedAccessException` を必ず再試行の対象に含めること。** `IOException` を継承していないため、`IOException` だけを捕まえる書き方では素通りする
- **書き込みは UI スレッドで行わない。** 再試行の待ちがそのまま画面の固まりになる。**値の写しだけ UI スレッドで取り、書き込みは投げる**（写しを取るのが UI スレッドでないと、書いている最中に画面側が値を変える競合になる）
  - **順番待ちごとバックグラウンドへ入れること。** `await gate.WaitAsync().ConfigureAwait(false)` と書いても、待たずに通れた場合は `await` がそのまま同期で続き、書き込みは UI スレッドに残る。**`ConfigureAwait(false)` が効くのは実際に中断したときだけ**である
  - **版番号で最新優先にする**（プレビュー生成・見積もりと同じ仕組み）。順序が入れ替わると直前の変更が巻き戻ったまま確定する。**結果（最後の値）を見るテストでは検出できない**ので、捨てた回数を数えて直接確かめる
  - **終了時だけは同期で待つ。ただし上限（数百 ms）を設ける。** 遅い媒体に置かれた exe だと閉じられなくなる。**設定が保存されることより、確実に終了することを優先する**
  - 打ち切りで残った一時ファイルは起動時に片付ける。ただし**「掴まれていないから消してよい」とは判断できない** — 書き終えてから `File.Move` するまでの一瞬は無防備で、そこを消すと相手の保存が失われる。**PID が生きていないこと**と**十分に古いこと**（1 時間）の両方を満たすものだけ消し、**迷ったら消さない側に倒す**

**多重起動時の既知の制約（不具合ではない）**

別々のフォルダを並行して処理したいことはあるため、**多重起動は許す**。その代わり設定については以下を受け入れる。**「設定が消える不具合」として調査に入らないこと。**

- **最後に終了したインスタンスの設定が残る。** 各インスタンスは自分が持っている設定の全体を書くので、後から保存したほうが前のものを丸ごと置き換える
- **設定は起動時に読み込んだきりで、インスタンス間で同期しない。** 他のインスタンスが保存しても、動いているインスタンスの画面は変わらない
- **項目ごとのマージは行わない。** 「片方が変えた項目だけを残す」には項目単位の更新時刻と競合解決が要る。設定を復元するという機能の価値に対して実装が重すぎる

これは 1 つのファイルに現在の状態をまとめて書くという設計から素直に出る帰結であり、その設計自体は「前回の続きから始められる」という目的に対して十分である。

## 画面構成

**作業は 1 ウィンドウで完結させる。ただし書き出しの設定と確認だけは、実行時にダイアログで行う**（不可逆な操作の前に必ず確認を通すため）。これは GIMP のようにウィンドウが散らばって何をすればいいか分からなくなる状態とは別物である。

```
┌─────────────────────────────────────────┐
│ [フォルダから追加] [クリア]       12 件    │
├───────────────┬─────────────────────────┤
│ ファイルリスト  │  プレビュー              │
│ (ここへドロップ) │  (選択中の1枚)           │
│  IMG_001.jpg  │                         │
│  IMG_002.jpg  ├─────────────────────────┤
│  ...          │  調整パネル（3分類）      │
├───────────────┴─────────────────────────┤
│ C:\out\IMG_001.jpg（12 件）  [書き出し...] │
└─────────────────────────────────────────┘
  IMG_001.jpg                    ← 状態表示（枠の外）
```

上部のプリセット行（`[プリセット ▼] [保存] [削除]`）は**まだ無い**。後述の理由で保留している。

最下段は**必ず 1 行**に収める。ダイアログへ切り出した目的が「調整パネルに縦を空ける」ことなので、ここで 2 行使うと目的を打ち消す。パスは `*` 列に置いて省略し、ボタンは `Auto` 列に置いて押し出されないようにする。

### 既定ウィンドウサイズ

**既定は 1100×990 論理px。ただし画面の作業領域に収まらなければそこまで縮める**（`MainWindow.FitToWorkArea`）。縮める方向にしか働かないので、広い画面では既定値がそのまま使われる。対で `WindowStartupLocation="CenterScreen"` にしてある — 既定の配置は左上からずらして開くため、作業領域いっぱいの高さだとずらしたぶん下端がはみ出す。

**990 という高さは「全項目が見える最小の高さ」から決めた。** 実測 2026-08-12（DPI 150%、9 項目、幅 1100）で、調整パネルの中身は 583.0 で、見えている高さは

```
見えている高さ = 割合 × (窓の高さ − 201.3)
```

| 割合 | 全項目が見える最小の窓高 |
|---:|---|
| 0.55（束 3 まで） | 1262 |
| 0.70 | 1034 |
| **0.75（現在）** | **979** |
| 1.00（プレビューを潰す） | 785 |

**測り直すときは `uishot` 相当の使い捨てプログラムで `ScrollViewer` の `ExtentHeight` と `ViewportHeight` を読む。**スクリーンショットの目視では「あと何 px 足りないか」が出ない。

**仮置きの行で見積もらないこと。** 束 4 の実装前に回転と枠線の行を模して測ったときは 550.4 で、実物は 583.0 だった。32.6 の差で既定サイズからはみ出し、割合を 0.70 から 0.75 へ上げ直すことになった。

**中身の高さは窓の幅でも変わる**（狭いと折り返しが増える）。9 項目では幅 1100 で 583.0、幅 1280 で 564.4、幅 720 で 670.8。**高さの解決策として幅を広げても割に合わない** — 1200 以上では 1 行分（18.7）縮んで打ち止めになる。

割合 0.70 では 1080p を 100% で使う環境（作業領域の高さ 1032 程度）でも足りない（必要 1034）。0.75 なら 979 で収まり、クランプ後の 1032 でも余裕がある。

#### 割合は「上限」であって「取り分」ではない

パネルの行は `Auto` なので、**パネルは中身が必要とする高さしか取らず、余りはプレビューへ行く**。実測（窓 1000×1000、割合 0.75）で、見えている高さは 0.75 × 798.7 = 599 ではなく中身と同じ高さで頭打ちになった。したがって**割合を上げても、背の高い窓ではプレビューは 1px も縮まない**。縮むのは中身が収まりきらない低い窓のときだけである。

その代わり**割合を上げた効きは低い窓に集中する**ので、`FractionConverter.Reserve`（プレビューに必ず残す高さ、160）で歯止めをかけている。これが無いと最小サイズ 720×600 でプレビューが約 119 まで潰れた（割合 0.55 のときは約 179）。`Minimum`（パネルの下限 140）とは向きが逆の下限で、**両方を満たせないほど窓が低い場合は `Minimum` を優先する**。

低い窓では `Reserve` のほうが先に効くため、**割合を 0.70 から 0.75 へ上げても、最小サイズや 1080p@150% での見え方は 1px も変わらない**（実測でどちらも 238.8 と 310.8 のまま）。割合の変更が効くのは既定サイズのように背の高い窓だけである。

#### 既知の限界: 小さい画面では全項目を見せられない

**1080p を 150% で使う環境（論理 1280×720、作業領域は約 672）には、9 項目は入らない。** この幅での中身は 564.4 で、割合を 1.0 にしてプレビューを完全に消しても 766 必要になる。4 つの案内文（リサイズ・グレースケール・二値化・シャープ・枠線）を全部消しても届かない。

実測では 9 項目のうち 6 項目まで見えて、残りはスクロールで届く。**この環境では初回起動時に全項目が見えないことを受け入れる。**項目を減らす・案内文を削る・プレビューを捨てるのはいずれも代償のほうが大きい。

「書き出し...」で開くダイアログ:

```
┌─ 書き出し（モーダル） ────────────────────┐
│ 出力先: [C:\out              ] [参照]     │
│ 形式:   [元の形式を維持 ▼]                │
│         JPEG 品質 [95]  WebP 品質 [95]    │
│         [ ] 可逆（サイズは大きくなります）  │
│ 透過は白で塗り潰されます                    │
│ ファイル名: [そのまま ▼]                   │
│ \ / : * ? " < > | は使えません              │
│ [ ] 同名のファイルを上書きする              │
│ 同名のファイルがある場合は別名で保存します    │
│ ┌──────────────────────────────────────┐ │
│ │ C:\out\IMG_001.jpg（12 件を処理）      │ │
│ │ うち 3 件を上書きします                 │ │  ← 警告色
│ │ 出力先のフォルダが見つかりません          │ │  ← 注意色
│ │ 8 / 12  IMG_008.jpg → IMG_008.webp    │ │  ← 実行中のみ
│ │ [████████░░░░]                        │ │
│ │ 10 件を書き出しました。2 件は失敗        │ │  ← 完了後のみ
│ └──────────────────────────────────────┘ │
│ IMG_003.jpg — 空き容量が足りません          │  ← 失敗時のみ
│ [詳細をコピー]                              │
│                          [実行] [閉じる]    │
└──────────────────────────────────────────┘
```

設定・実行・進捗・結果を 1 か所で完結させる。押した場所と結果が出る場所が違うと操作として不自然になるため。

**内側の枠は、見積もり・進捗・結果が排他で使う。** そしてどれが出ているかが実行前の再確認の判定根拠になっている（「安全ガード（必須）」参照）。この図はその構造を示すために置いてあるので、**表示まわりを変更するときは図と実装の両方を合わせること**。構造を誤解したまま触ると原則 2 に触れる。

**ボタンは常に 2 つ。** 実行中は「実行」が同じ位置で「キャンセル」に入れ替わる。押せない操作を並べない。

**失敗一覧のために場所を予約しない。** 大半の実行では失敗が無いため、初期の高さは失敗なしの状態に合わせ、失敗が出たときにだけ窓を広げる。

リストで選んだ 1 枚がプレビューに表示され、そこで調整した内容が全件に適用される。「1 枚を調整する体験」と「一括適用」を同じ画面で両立させる。

画面を分ける根拠は、**調整は連続的に触るもの、出力は実行ごとに一度決めるもの**で性質が違うこと、そして**調整パネルに縦の場所を確保する**ためである。
